# Sprint 2 — Provenance Evidence Investigation

**Scope:** Repository files and available Git history; no data or source changes
**Status:** Investigation report; no provenance join is promoted to verified
**Purpose:** Identify existing source, construction, ordering, and diagnosis evidence and the exact gaps remaining.

## 1. Executive findings

The repository points to the Dresden EEG cohort’s OSF project, `https://osf.io/6594x/`, and contains scripts that can list/download files from that project and print its `readme.txt`. Project documentation says the OSF README explains that the large sample data was split across files. The actual README, an archived OSF listing/API response, and immutable file-download URLs are not preserved in the repository.

No original MATLAB script or other source procedure for constructing `d1.mat`–`d7.mat` was found in the repository or reviewed Git history. No authoritative per-trial table connecting EEG trial locators to `y_stim` columns was found. The current `TrialManifest` encodes a deterministic numeric-file-order/metadata-column-order crosswalk; the mapping-validation script tests that proposed crosswalk but does not establish an independent key.

The paper reports that the cohort was clinically classified and provides aggregate counts, but the repository contains no participant-level clinical diagnosis table keyed to stable participant identifiers. `sub_name_stim.mat` is described as three ordered filename blocks; sorting and matching block sizes do not prove that filename ordinal is participant index or diagnosis. `y_stim` one-hot rows must not be used as diagnostic labels.

**Bottom line:** The available repository evidence is useful for locating the public source and documenting candidate structure. It does not recover the authoritative construction procedure, trial ordering, participant identity crosswalk, or participant-level diagnostic mapping required to validate a research split.

**Terminology boundary:** `(source_filename, within_file_trial_index)` is a source-local trial locator. The configured block plus row-0 value yields only a `candidate_participant_id`; the configured block itself yields only a `candidate_diagnostic_group`. Neither establishes a verified participant identity or clinical diagnosis. Verified clinical labels need an authoritative participant-level source linked to the trial locators; `y_stim` rows 1–3 are not diagnostic targets.

## 2. Evidence status vocabulary

| Status | Meaning here |
|---|---|
| **Authoritative** | A primary source for the limited fact stated (for example, the paper for what it reports, or OSF as the dataset location). This does not imply authority for a different relationship not keyed by that source. |
| **Indirect** | Consistent documentation or structural evidence exists, but it does not directly key or establish the relationship at issue. |
| **Candidate** | A proposed deterministic interpretation or join used by project code/reports, not independently confirmed. |
| **Unresolved** | No adequate evidence in the inspected repository or history establishes the relationship. |

This investigation searched tracked project files, the local project documentation/scripts, the available local dataset inventory, and Git history. It did not call OSF, contact authors/custodians, inspect external archives, or revalidate EEG values.

## 9. Evidence requests to unblock provenance

Request and preserve the following from the OSF maintainer, data custodian, or original research team:

1. The exact OSF README and project/file listing version used for acquisition, including file IDs, versions, timestamps, sizes, and checksums.
2. The MATLAB/Octave/source procedure that generated `d1.mat`–`d7.mat`, including source array ordering, split axis, offsets, and whether metadata was permuted or chunked alongside EEG.
3. An authoritative all-trial key mapping `(source file, within-file trial index)` to the `y_stim` column or an equivalent stable original trial identifier.
4. An authoritative participant key mapping each `y_stim` row-0 run to a stable participant identifier and to the corresponding `sub_name_stim` filename, including how filename order was generated.
5. A participant-level clinical diagnosis record (or official coding guide) linked by that stable identifier, with diagnosis definitions and documented exclusions/ambiguous cases.
6. Any supplementary data dictionary, source archive, trial logs, or ethics-approved data documentation that explains the fields and mapping procedure.

Matching counts, file timestamps, filename sorting, contiguous row-0 runs, and candidate-selected signal correlations may support these investigations, but none substitutes for the independent source key. Until the requested materials are obtained and reviewed, maintain all participant/diagnosis joins as candidate or unresolved and do not use them to create research partitions.

## 10. Investigation boundary

No source code or data was modified. No file was downloaded from OSF during this investigation, no participant identifier or diagnostic label was created, and no split was generated. This report describes repository evidence and gaps; it does not verify candidate mappings or claim scientific validation.
